## 4. Методика ранжирования (чтобы порядок был воспроизводимым, а не «на глаз»)

Каждый пункт получает 5 баллов по шкале 1–5, приоритет = `(K1·2 + K2·2 + K4) / K3`, где:

- **K1 — объём**: сколько символов/строк уйдёт (5 = ≥ 100 000 симв., 4 = 30–100 тыс., 3 = 10–30 тыс., 2 = 3–10 тыс., 1 = < 3 тыс.).
- **K2 — кратность**: во сколько раз уменьшится число мест, где это правится (5 = 20+ файлов или 10+ копий кода, 1 = один файл).
- **K3 — риск/сложность**: 1 = изолированно и покрыто проверкой; 5 = меняет разметку/поведение десятков страниц без тестов.
- **K4 — эффект для пользователя**: 5 = ускоряет загрузку всех страниц (кэш, вес, лишние запросы); 3 = ускоряет одну тяжёлую страницу; 1 = только читаемость кода.

Округление до 0.1, сортировка по убыванию. При равенстве — выше тот пункт, у которого меньше K3. Обязательно указать «база замера» (что мерим до и после: `tools/inventory.py`, DevTools Network размер+время, число файлов с inline-JS).

### 18.2 Решение о канонизации (уточнение правила §14.2 п.1)

Правило 2a «переносим только дословно идентичное тело» в `fractions` даёт **ноль**: ни одно объявление `gcd`/`lcm`/`getRandomInt` не совпадает с модулем посимвольно (4, 2 и 2 варианта тела соответственно), а `primeFactors` отличается реализацией цикла.

Решение: правило **разделяется по типу функции**:

- **Чистая функция** (нет DOM, нет глобального состояния, только аргументы → значение) — тело можно нормализовать к канону модуля, **если эквивалентность подтверждена численным харнессом**. Сюда входят `gcd`, `lcm`, `getRandomInt`, `pickRandom`, `primeFactors`.
- **Функция с DOM/разметкой/цветом раздела** (`animate`, `startConfetti`, `showVictory`, `setFeedback`, `fireConfetti`, `simplifyFraction`, `getFactors`) — по-прежнему только дословное совпадение, иначе остаётся локальной.

Проверки эквивалентности (харнесс в `%TEMP%`, не в репозитории; как в 2a):

| что сверяем | диапазон | критерий |
|---|---|---|
| `gcd`: 4 варианта страниц ↔ модуль | `a, b ∈ 1..300` (90 000 пар) | 0 расхождений |
| `lcm`: `Math.abs(a*b)/gcd` ↔ `(a*b)/gcd` | `a, b ∈ 1..300` | 0 расхождений (все вызовы — положительные знаменатели) |
| `primeFactors`: вариант `multiplication` ↔ модуль | `n ∈ 2..5000` | массивы совпадают по составу и порядку |
| `getRandomInt`: 1 000 вызовов, `min > max` не встречается | `[3,7]`, `[1,1]`, `[2,9]` | все значения целые и внутри диапазона, обе границы достигаются |

Изменение канона в модуле (единственное в этом шаге):

```js
// было (2a):  function lcm(a, b) { return (a * b) / gcd(a, b); }
// станет:     function lcm(a, b) { return Math.abs(a * b) / gcd(a, b); }
```

Причина: `Math.abs` уже есть в `addition`/`comparison`, для страниц 2a (`gcd`/`lcm` раздела `divisibility`) результат не меняется (все аргументы положительные), зато после шага в проекте один вариант `lcm`, а не три.

Практическое следствие для 2c: `gcd`/`lcm`/`getRandomInt`/`pickRandom`/`primeFactors` больше не переписываются — страницы следующих разделов просто теряют объявления и подключают модуль (плюс сверка `primeFactors` из `percents`, где 2 других варианта тела).

| 4 (разы → %) | k = 1,5; 2; 2,5; 3; 5 | (k−1)·100 = 50; 100; 150; 200; 400% |
| 6 (сложный процент) | P кратно 10 000, r ∈ {10, 20, 25, 50}, n ∈ {2, 3} | 10 000·1,2³ = 17 280; 10 000·1,25² = 15 625; 20 000·1,1³ = 26 620 |

| 8 (пропорции) | a, b, c из таблицы кратных | x — целое, произведения диагоналей совпадают |

Если сгенерированное значение не даёт «красивого» ответа — пара бракуется и генерируется заново (лимит 200 попыток, затем fallback-пара из таблицы). Это дешевле, чем потом объяснять «≈36,666…%».

- Принимаем и `,` и `.` как десятичный разделитель (`value.replace(',', '.')`), сравнение с эталоном с допуском `±0,005` (ответы до сотых).

### 23.1 Решение по семантике (принято, в реализации не пересматривается)

### 23.3 Ключ и схема хранения

Один ключ на весь сайт: `mg6.progress.v1` (других не добавляем).

```json
{ "v": 1, "updated": 1763500000000,
  "m": { "gcd": { "s": 1763499000000, "w": 3, "l": 1763499999999, "d": 1763500000000 } } }
```

`s` — первый старт, `w` — число побед/решённых серий, `l` — последняя активность, `d` — время завершения (есть только у `done`). 30 миссий × ~90 байт ≈ 3 КБ при лимите 5 МБ — запас огромный; версия и в ключе, и в поле `v` (при `v != 1` старые данные игнорируем и перезаписываем, без миграций).

Все обращения — в `try/catch`: `SecurityError` (приватный режим/Safari, запрет cookies) и `QuotaExceededError` не должны ломать тренажёр. При ошибке пишем в память и продолжаем (прогресс просто не сохранится), в консоль — один `warn`, не `error`: `page_console.py` падением считает только текст по `ERROR_RE` (`Uncaught|Unhandled|is not defined|is not a function`), так что `console.error` его формально не уронит, но `warn` не пугает ученика и не шумит в логе.

### 23.4 API: `MissionStore` + `trackGoal` в `assets/analytics.js`

```js
// assets/analytics.js, рядом с RewardSystem
window.MissionStore = {
    KEY: 'mg6.progress.v1',
    read() { /* JSON.parse + try/catch + проверка v */ return { v: 1, m: {} }; },
    write(state) { /* merge по id, updated = Date.now(), try/catch */ },
    record(goal, params) { /* таблица событий ниже */ },
    get(id) { return this.read().m[id] || null; },
    reset() { /* localStorage.removeItem(KEY) */ }
};

window.trackGoal = function (goal, params) {
    if (window.MissionStore) window.MissionStore.record(goal, params || {});
};
```

|---|---|---|
| `trainer_started` | `s ??= now` | `opening.html:821` |
| `task_solved`, `reward_shown` | `w++`, `l = now` | `opening.html:756`; `showWin` (автоматически) |
