## 1. Что должно получиться (результат задачи)

План без измерений не принимается: каждый пункт должен опираться на цифры из раздела «Факты» или из новых замеров шага 6.2–6.3.

## 4. Методика ранжирования (чтобы порядок был воспроизводимым, а не «на глаз»)

Каждый пункт получает 5 баллов по шкале 1–5, приоритет = `(K1·2 + K2·2 + K4) / K3`, где:

- **K1 — объём**: сколько символов/строк уйдёт (5 = ≥ 100 000 симв., 4 = 30–100 тыс., 3 = 10–30 тыс., 2 = 3–10 тыс., 1 = < 3 тыс.).
- **K2 — кратность**: во сколько раз уменьшится число мест, где это правится (5 = 20+ файлов или 10+ копий кода, 1 = один файл).
- **K3 — риск/сложность**: 1 = изолированно и покрыто проверкой; 5 = меняет разметку/поведение десятков страниц без тестов.
- **K4 — эффект для пользователя**: 5 = ускоряет загрузку всех страниц (кэш, вес, лишние запросы); 3 = ускоряет одну тяжёлую страницу; 1 = только читаемость кода.

Округление до 0.1, сортировка по убыванию. При равенстве — выше тот пункт, у которого меньше K3. Обязательно указать «база замера» (что мерим до и после: `tools/inventory.py`, DevTools Network размер+время, число файлов с inline-JS).

## 6. Стартовые гипотезы (НЕ утверждённый план, проверить в 6.2–6.4)

1. **Inline-JS в HTML (602 803 симв. в 41 файле)** — главный резерв по объёму и по кэшу: вынос общих утилит в `assets/*.js` уменьшает суммарный вес и число копий. Гипотеза №1 по приоритету.

6. **Тяжёлые страницы**: `equations_construct.html` (81 101 симв., 62 `on*`), `number-by.html` (53 693), `area-metaphor.html` (44 234), `index.html` (41 519 + 16 333 inline-CSS) — локальный выигрыш выше среднего, но правки затрагивают учебную логику (риск выше).
